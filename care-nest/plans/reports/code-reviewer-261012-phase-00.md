## Overall Verdict: **NEEDS_FIXES**

Phase 0 delivers a working monorepo skeleton with a high-quality Wonlex codec that closely matches the Dart reference. **All 5 packages build, lint, type-check, and 90 unit tests pass.** However, the work deviates significantly from explicit NFRs in the Phase 0 plan: schema uses CUID instead of UUID v7, 6 plan-required entities are missing, no CD pipeline / CODEOWNERS, and several Phase 0 deliverables (shared-kafka, shared-redis) are not present. Also, the iot-codec barrel export has a documentation bug in its usage example.

## Critical Issues (must fix before Phase 1)

### C1. NFR-0.2 violation — schema uses CUID, not UUID v7
**File:** `packages/database/prisma/schema.prisma` (all 13 models)
Plan NFR-0.2 mandates: *"Tất cả primary key phải dùng UUID v7 ... thay vì auto-increment integer"*. Every model in the schema uses `@default(cuid())` instead. This is a foundational decision that affects distributed mergeability, ID-leak prevention, and the multi-tenant middleware that the plan describes for Phase 1.
**Fix:** Set `default(uuid())` (Prisma 5 supports v4 out-of-box) or wire `uuidv7()` via `previewFeatures = ["driverAdapters"]` + a `@default(dbgenerated("uuidv7()"))` raw. Add a migration step.

### C2. Missing 6 of 12 plan-required entities
**File:** `packages/database/prisma/schema.prisma`
Plan NFR-0.1/0.3 + FR-0.6 list 12 entities: User, Seller, Product, Order, Device, Subscription, Payment, Shipment, Caregiver, Notification, AuditLog, SellerKycDocument. Schema implements 13 **different** entities: User, Seller, **Category**, Product, **ProductImage**, **Inventory**, Order, **OrderItem**, Payment, Device, **DeviceAssignment**, **HealthRecord**, **Alert**.

Missing required models:
- `Subscription` (FR-0.6 + recurring-revenue core)
- `Shipment` (FR-0.6 + GHN integration in Phase 2)
- `Caregiver` (FR-0.6 + caregiver UI in Phase 1)
- `Notification` (FR-0.6 + multi-channel comms in Phase 2)
- `AuditLog` (NFR-0.3: required 7 fields, 7-year retention, "non-modifiable")
- `SellerKycDocument` (FR-0.6 + KYC workflow in Phase 1)

NFR-0.3 is unsatisfied because there is no AuditLog at all.
**Fix:** Add the 6 missing models. The schema can keep the 6 new models it has (Category, ProductImage, etc. are useful) but must add the 6 listed in the plan.

### C3. `shared-kafka` and `shared-redis` packages do not exist
**Plan:** Steps 34-35 require `packages/shared-kafka` (KafkaJS producer/consumer + DLQ) and `packages/shared-redis` (ioredis + TTL helpers) by end of Week 4. README `README.md:39-40` advertises them as part of the project structure. Neither package is in `packages/`.
**Fix:** Either implement them (Phase 0 scope per plan) or remove from README and document as Phase 1 deliverables. Right now README is misleading.

### C4. CD pipeline and CODEOWNERS missing
**Plan:** Steps 19 + 26 + 26 require `cd-staging.yml` (auto-deploy on main) and `CODEOWNERS` (CTO approval). `.github/workflows/` only has `ci.yml` and `commit-lint.yml`.
**Fix:** Add `.github/workflows/cd-staging.yml` and `.github/CODEOWNERS` (or defer to Phase 1 with an explicit ADR).

### C5. CI runs pnpm 9 but root pins pnpm 12.11.2
**Files:** `package.json:6` (`"packageManager": "pnpm@12.11.2"`) vs `.github/workflows/ci.yml:22` (`version: 9`).
pnpm 9 will refuse to install a lockfile generated by pnpm 12 (`ERR_PNPM_LOCKFILE_CONFIG_MISMATCH` or auto-update warning), so either:
- the lockfile will get silently regenerated under pnpm 9 (drift), or
- CI will fail when running `pnpm install --frozen-lockfile` on a freshly-pinned pnpm 12 lockfile.

Also `pnpm-workspace.yaml:6` uses `allowBuilds:` which was added in pnpm 10 — silently ignored by pnpm 9.
**Fix:** Bump CI `version: 12` (or remove `packageManager` pin to a version that matches the lockfile). Add `.npmrc: package-manager-strict=false` only if intentional drift is desired.

### C6. iot-codec barrel example uses a non-existent API
**File:** `packages/iot-codec/src/index.ts:17-21`
```ts
const parsed = parsePacket(out);
if (parsed.ok) {                  // ❌ parsePacket returns ParsedPacket | null, not { ok, packet }
  const typed = decodePacket(parsed.packet);  // ❌ .packet is undefined
  console.log(typed.command);
}
```
`parsePacket` in `codec.ts:58` returns `ParsedPacket | null`. There is no `.ok`/`.packet` discriminator anywhere in the codebase. Anyone copy-pasting the README example will get a TypeScript error AND a runtime `undefined.command`.
**Fix:** Update the example to `if (parsed) { const typed = decodePacket(parsed); ... }`.

### C7. Coverage tool not installed; CI never enforces >95%
**Plan:** Step 31 says *"target coverage >95%".* The plan's success criteria for Phase 0 explicitly state *"Codec library `packages/iot-codec/` có unit tests pass với coverage >95%"*.
**Files:** `packages/iot-codec/vitest.config.ts:8-14` sets thresholds and `provider: 'v8'`, but `@vitest/coverage-v8` is not in `package.json` devDependencies. Running `vitest run --coverage` fails with `MISSING DEPENDENCY '@vitest/coverage-v8'`. The CI workflow also never calls `vitest --coverage` — only `vitest run`. The 80% threshold is effectively dead code.
**Fix:** Add `@vitest/coverage-v8` to devDependencies and a `coverage` task to turbo.json; bump CI to run `vitest run --coverage` (or `turbo run coverage`) and gate the build on the threshold.

### C8. `.npmrc` deviation from plan
**Plan:** NFR-0.5 / step 15: `shamefully-hoist=false` is the project standard (hoisting hides missing peer deps and breaks pnpm's strict resolution).
**File:** `.npmrc:1` sets `shamefully-hoist=true`. This will mask future peer-dep bugs and slow `pnpm install` for monorepo.
**Fix:** Flip to `false` (or document the deviation in an ADR if intentional for a specific dep).

## Improvements (should fix)

### I1. `extractPackets` accepts arbitrary `[…]` content
**File:** `packages/iot-codec/src/utils/buffer.ts:21-36`
The function does `indexOf('[')` / `indexOf(']')` and returns whatever sits between. It will happily return `garbage[some text]` as a "packet" if such bytes appear in the stream (e.g. binary noise, CRLF in HTTP-style probes). `parsePacket` then rejects it — wasted CPU. Tighter version: validate against `PACKET_RE` inline so the buffer only retains valid-looking envelopes.

### I2. `appendChunk` silently drops data on overflow
**File:** `packages/iot-codec/src/utils/buffer.ts:46-54`
The JSDoc says *"Throws if the buffer overflows"*, but the implementation returns `''` — the entire accumulated buffer is lost without throwing or erroring. A malformed attacker can cause a memory DoS by sending >4 KB of unparseable bytes; the gateway will silently drop everything.
**Fix:** Either throw `BufferOverflowError` (so the gateway can close the connection) or surface a structured `{ ok: false, dropped: N }` return so callers can log + close. Update the JSDoc either way.

### I3. Mock server writes `\n` separator that the codec never expects
**File:** `packages/iot-codec/src/server/mock-server.ts:78-80, 109`
The Dart reference (`wonlex_protocol.dart`) does not delimit packets with `\n` — the bracketed envelope is the only framing. The mock server adds `\n` between packets. It works because `extractPackets` ignores `\n`, but the real device will NOT send newlines; the gateway's parser must not start depending on them.
**Fix:** Drop the `\n` from the mock server (or add a `delimited: true` option, default off, with documentation).

### I4. Mock server duplicates `PACKET_RE` regex inline
**File:** `packages/iot-codec/src/server/mock-server.ts:100`
`/^\[3G\*(\d{10,15})\*([0-9A-Fa-f]{4})\*(.*)\]$/` is a copy of `PACKET_RE` from `utils/regex.ts`. If the spec ever changes (e.g. allow longer device IDs) the mock server will silently drift.
**Fix:** `import { PACKET_RE } from '../utils/regex.js'` and use it.

### I5. `parseLocation` silently coerces unknown `fix` to `'V'`
**File:** `packages/iot-codec/src/packets/location.ts:56`
`const fix: 'A' | 'V' = fixRaw === 'A' ? 'A' : 'V';` accepts `'X'`, `' '`, `'a'` and pretends it's `'V'`. The type lies — the function should reject values that aren't A or V.
**Fix:** `if (fixRaw !== 'A' && fixRaw !== 'V') return null;`

### I6. `parseVitalsOxygen` and `parseVitalsTemperature` skip range checks
**File:** `packages/iot-codec/src/packets/vitals.ts:71-98`
- Oxygen allows 0-1000+ (no clamp or validation)
- Temperature allows any float (-50 to 200 — clinically meaningful range is ~30-45°C)
Either is a clinical-data correctness risk for a health-monitoring platform.
**Fix:** Add range checks: `if (oxygen < 0 || oxygen > 100) return null;`, `if (temperature < 25 || temperature > 45) return null;`.

### I7. `decodePacket` silently swallows typed-decode errors
**File:** `packages/iot-codec/src/packets/index.ts:18-43`
The `?? packet` fallback means a malformed heart-rate packet still comes out as `command: 'heartbeat'` with `params: ['abc', '0', '85']`. The downstream consumer (Kafka producer, alert engine) has no way to know the typed decode failed.
**Fix:** Return a discriminated union: `{ ok: true, packet: AnyPacket } | { ok: false, error: string, raw: ParsedPacket }` and let the gateway route errors to a DLQ topic.

### I8. `appendChunk` is the wrong API for streaming
**File:** `packages/iot-codec/src/utils/buffer.ts:46-54`
Current signature `appendChunk(buffer, chunk) → buffer` makes the caller manage state. The natural streaming API would be a class: `new PacketBuffer(max).push(chunk) → Packet[]` with built-in overflow handling. This avoids the silent-flush bug (I2) and is more ergonomic at the call site.
**Fix:** Introduce a `PacketBuffer` class; deprecate the free function.

### I9. Dockerfile.service assumes services in `packages/`, not `services/`
**File:** `infrastructure/docker/Dockerfile.service:48`
`COPY --from=build ... /app/packages/${SERVICE}/dist ...` but `pnpm-workspace.yaml` has `services/*` and the only `iot-gateway` lives in `services/`. Building `auth-service` will fail with "no such package".
**Fix:** Either move services to `packages/` (rename to `packages/services/auth-service`) or change the COPY path to `services/${SERVICE}/dist` (as the iot-gateway Dockerfile does).

### I10. K8s dev config is placeholder-thin
**File:** `infrastructure/k8s/dev/config.yaml`
Plan steps 21-23 require PG+Timescale, Kafka 3.7 KRaft, Redis 7 StatefulSets. Only `namespace.yaml` and a single `ConfigMap/Secret` are present. No PG, Kafka, Redis, Grafana, Prometheus, Loki manifests.
**Fix:** Add the StatefulSets, or mark this as "Phase 3" and update the plan.

### I11. K8s Secret has placeholder JWT_SECRET committed
**File:** `infrastructure/k8s/dev/config.yaml:23`
`JWT_SECRET: replace-me-with-a-32-byte-random-string` in `stringData`. While `stringData` doesn't get hashed into git in plain kustomize, this is a misleading template for a fresh dev env — the dev stack will boot with a known-weak secret. Use a `SealedSecret` or inject from Vault.
**Fix:** Add a comment "DO NOT use in production"; consider `valueFrom: { secretKeyRef: { name: carenest-dev-secrets-real, key: jwt } }` instead of literal value.

### I12. Service names listed don't match the planned topology
**File:** `packages/shared-config/src/constants.ts:5-16`
Includes `INVENTORY_SERVICE`, `HEALTH_SERVICE`, `ANALYTICS_SERVICE` — none of which appear in the Phase 0 plan. The plan lists auth, catalog, order, payment, device, notification, iot-gateway, alert-engine. A future developer grepping for "inventory-service" in code will find nothing.
**Fix:** Trim to the 8 plan-listed service names.

### I13. README structure lies about packages and infra
**File:** `README.md:23-53`
Lists `shared-kafka`, `shared-redis`, `ui`, `tools/`, `infrastructure/terraform/` — none of these exist. Newcomers will be confused.
**Fix:** Update README to match the actual layout OR add a `// TODO: Phase 0/N` marker on each absent block.

### I14. Mock server's `idleTimer` does not get cleared on close
**File:** `packages/iot-codec/src/server/mock-server.ts:85-90`
The 30-second idle timer is `unref()`-ed (good — won't block process exit) but is never `clearTimeout()`-ed when the server actually closes. A test that spins up multiple mock servers could leak timers in CI.
**Fix:** Track the timer in the closure and `clearTimeout` it inside `server.close()` listener.

### I15. `decodePacket` switch could be exhaustive
**File:** `packages/iot-codec/src/packets/index.ts:18-43`
Uses a runtime switch on string. With `commandName` typed as `string` and `command` typed as `CommandType`, TypeScript cannot enforce exhaustiveness. Consider a `Record<CommandType, (p: ParsedPacket) => AnyPacket | null>` lookup so an unknown command fails at compile time.

## Style Nits

1. `parseVersion` (`version.ts`) takes 14 lines for a 4-line decoder — could fold into `sos.ts` ("alert & meta").
2. `loginType: string` (`types/packets.ts:51`) — should be a narrow union (per Wonlex manual: `'0'` is a regular login, others are admin/OTA).
3. The 14-arg destructure in `parseLocation` (`location.ts:19-34`) has 14 lines of `if (... === undefined) return null` guards. Could use early-exit: `if (packet.params.length < 14) return null;` is already there, so the individual checks are redundant — TS's `noUncheckedIndexedAccess` would catch the rest.
4. `enable-timescale.ts:19-24` uses `prisma.$executeRawUnsafe` with table/column names interpolated as strings. If anyone ever parameterizes the function, this becomes a SQL injection vector. Use `prisma.$queryRaw` with tagged template literals instead.
5. `parseVersion: versionString: packet.payload` (`version.ts:13`) — if the version string ever contains a comma, this silently includes the trailing fields. Test edge: `VERNO,1.0,beta` would store `1.0,beta` as version (probably correct), but the spec says no commas.
6. `retry.ts:67` — `throw lastError;` is unreachable per the loop contract. Mark with `// unreachable` or use a `while (true)` with `if (attempts <= 0) throw lastError;` pattern for clarity.
7. `withTimeout.ts:14-23` — `setTimeout` handle is cleared in `finally`, but if `clearTimeout` itself throws (it doesn't, but lint rules differ), the original error is lost. Add a try/catch.
8. `mock-server.ts:71-73` — `eslint-disable-next-line no-console` is fine, but consider a structured logger (already exists in shared-utils) so the server is log-injection safe.
9. `parseHeartbeat` repeats the destructure-then-validate pattern of every other decoder. Consider a `parseIntParams(packet, count)` helper.
10. The `extractPackets` function name is slightly misleading — it both extracts and splits by `]`; consider `extractCompleteEnvelopes`.
11. `pnpm-workspace.yaml:7-11` — comment out `allowBuilds` with a one-line rationale, since the field is pnpm 10+ only (see C5).
12. `apps/.gitkeep` and `services/.gitkeep` are the only files in those directories. Add a top-level `apps/README.md` and `services/README.md` describing the planned layout.

## Positive Observations

- **Codec matches the Dart reference faithfully.** 10-15 digit IMEI regex, `[3G*…*…*…]` envelope, 4-char uppercase hex of UTF-8 byte length, `content.split(',').first` for command name. The Dart returns `null` for malformed input; TS does the same. Behaviorally interchangeable.
- **Branded types are tasteful.** `DeviceId` brand prevents accidental cross-pollution at type level without runtime cost.
- **Mock server is split into a subpath entry** (`./server` in `package.json:25-29`) so production bundles can avoid pulling in `node:net`. Documented intent in `src/server/index.ts`.
- **Per-command parsers** (`packets/login.ts`, `packets/heartbeat.ts`, etc.) are individually testable and well-scoped — each <30 LoC.
- **PII masking helpers** (`pii.ts`) are the right shape for the PDPA-driven threat model in NFR-0.4.
- **`retry` with AbortSignal** (`retry.ts:43-65`) is correctly implemented and tested.
- **Pino logger with pretty-print toggle** (`logger.ts:46-58`) — production-safe default, dev-friendly on TTY.
- **TimescaleDB `if_not_exists => TRUE`** (`enable-timescale.ts:22`) — idempotent, safe on every boot, matches plan intent.
- **Turbo cache hits show the build is working as designed** — the 5/5 cached run took 100ms.
- **Test count of 90 with all passing** (45 in iot-codec, 15 each in shared-{config,types,utils}) — meets the FR-0.8 "unit tests pass" success criterion.
- **`.gitignore`** correctly excludes `.env*`, `node_modules`, `dist`, `.turbo`, `coverage` — common leak vectors.
- **`.env.example`** uses clear placeholder strings (`replace-me-with-32-byte-random-string`) and lists the full set of expected env vars.
- **Multi-entry `tsup`** config in `iot-codec/tsup.config.ts:3-9` enables tree-shaking and code-split entry points.
- **Vietnamese-aware helpers** — `vnPhoneSchema` strips spaces/dashes/dots, `maskVnPhone` normalizes `+84` to `0`. CareNest is a VN-first product and this is the right level of care.
- **Conventional commit enforcement** via commitlint + `wagoid/commitlint-github-action@v5` is set up.
- **Concurrency-cancel on `ci.yml`** is enabled (`cancel-in-progress: true`) — saves CI minutes on rapid pushes.

## Unresolved Questions

1. **Is the "12 entities vs 13 entities" deviation deliberate?** The plan lists 12 specific models; the schema has 6 of those + 6 new ones. If the team is consciously evolving the data model, an ADR would help. If it's an oversight, the missing models need to be added.
2. **CUID vs UUID v7 — technical or preference?** Prisma 5 supports `uuid()` (v4) out of the box but not v7 natively; a v7 implementation requires `dbgenerated("uuidv7()")` and a Postgres extension (e.g. `pg_uuidv7`). Is the team OK with the migration friction, or willing to accept CUID?
3. **Where is `services/iot-gateway`?** Two Dockerfiles reference it but the directory contains only `.gitkeep`. Is it scaffolded-but-empty, or aspirational?
4. **Why does `apps/` exist at all in Phase 0?** No app is implemented. Is this reserved for Phase 2?
5. **What's the password for `MEILISEARCH_MASTER_KEY` in `k8s/dev/config.yaml`?** It's committed as plain text. Is `SealedSecret` / `External Secrets Operator` on the roadmap?
6. **Is the `default 4096-byte` max buffer per device connection, or per gateway?** A per-gateway cap of 4 KB is far too small for 10K concurrent devices (per plan FR-0.8). The constant `IOT.MAX_BUFFER_SIZE = 4096` is currently in `shared-config/src/constants.ts:62` but the comment in `buffer.ts:12` implies per-stream. Clarify.
7. **Why is `commit-lint.yml` triggered only on `pull_request`?** Convention commits are useful to check on every push so a broken branch is caught early. Minor.
8. **The `payment-service` exists as a `SERVICE_NAME` constant but is missing from the plan's service list for Phase 1** (Phase 1 plan: auth, catalog, order, device, alert, plus iot-gateway). When does payment arrive?
